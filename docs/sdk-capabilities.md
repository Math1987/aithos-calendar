# SDK capabilities audit: what the A2A and AI Catalog SDKs provide

Audited on 2026-09-18 against the latest published versions. The question
for every row is the same: *is this capability provided by the SDK, so that
this proof of concept can call it instead of implementing it?* The rule
applied to this repository is **reuse whatever an SDK provides; implement
only what is missing; keep the home-made parts isolated for an upstream
contribution** (`src/trust/jose.rs`, `src/trust/card.rs`,
`src/trust/verify.rs`).

## What the specifications say

**A2A 1.0, §Agent Card Signing** ([spec](https://a2a-protocol.org/latest/specification/)). The content to sign is the card canonicalized with JCS (RFC 8785); "the `signatures` field itself MUST be excluded from the content being signed"; optional fields that were not set and fields at their default value MUST be omitted. Each `signatures[]` element is a JWS in JSON-serialization style with a detached payload: `protected` (base64url JSON header), `signature` (base64url), optional unprotected `header`. Header parameters: `alg` and `kid` required, `typ` SHOULD be `JOSE`, `jku` optional (URL of a JWK Set). Verification: extract a signature, retrieve the key by `kid` and `jku`, remove `signatures`, canonicalize, verify. "Clients SHOULD verify at least one signature before trusting an Agent Card."

**AI Catalog, §Trust Manifest and §Signature Verification** ([spec](https://github.com/Agent-Card/ai-catalog/blob/main/specification/ai-catalog.md)). Remove `signature`, canonicalize with JCS, sign the canonical bytes as a detached JWS in compact serialization (`header..signature`). `none` and HS* MUST be rejected; the allow-list is `ES256, ES384, EdDSA, PS256, PS384, RS256`; "consumers MUST NOT let the `alg` header alone select a verification algorithm". The catalog-level `signature` is "verified exactly as a Trust Manifest signature". Key resolution follows the `identity` URI scheme; for an HTTPS URL: "Fetch the JWK Set at the specified URL and select the key matching the JWS `kid` header." `jku`, `x5c` and `x5u` are not mentioned. A draft change ([PR #117](https://github.com/Agent-Card/ai-catalog/pull/117)) proposes `trustManifests[identity]` with field-selective signatures; this repository follows the published text.

## Consequences for this repository

- **Reused from SDKs.** `ai-catalog` types and domain-alignment helpers; `ai-catalog-validate` for the conformance level in tests; `ai-catalog-trust::verify_digest` in the verifier and `analyze_catalog` in tests; `serde_jcs` (the same JCS crate the AI Catalog SDK uses) for canonicalization; the A2A Rust SDK for every protocol type and transport.
- **Implemented here because no Rust SDK provides it.** ES256 detached JWS production and verification (`src/trust/jose.rs`), A2A card signing and verification with `kid`/`jku` handling (`src/trust/card.rs`), manifest and catalog signing (`src/trust/manifest.rs`, `src/trust/mod.rs`), and the ordered consumer-side checks (`src/trust/verify.rs`). These files depend only on `serde_json`, `serde_jcs`, `base64ct`, `p256`, `sha2` and could be proposed upstream as an `ai-catalog-jws` crate (manifest/catalog side) and as a signing module for `a2a-rs` (card side).
- **Deliberate deviation.** Canonicalization is applied to the raw `serde_json::Value`, not to the typed structs, so the signed bytes are exactly the served bytes even when a document contains explicit empty arrays (issue #26 above). A unit test (`trust::manifest::sdk_equivalence`) checks that on this service's documents the SDK's `canonicalize_trust_manifest` and `canonicalize_catalog` reproduce our signing payloads byte for byte, so a consumer built on the SDK verifies our signatures.
- **Interoperability note for A2A cards.** The Python and JavaScript SDKs strip empty values from the card before canonicalizing (`_clean_empty`, `cleanEmpty`). The Rust SDK serializes the card as-is (for example `"capabilities":{}`), and this service signs exactly what it serves. A Python or JavaScript verifier may therefore recompute a different payload for a card that contains empty containers. This is recorded as a limitation in `docs/trust-manifest-evaluation.md`; the cross-SDK check belongs to the scenario lab.
- **Rust SDK 0.3.1 cannot read an omitted `StringList.list`.** A2A's JSON mapping omits an empty scope list (`{"schemes":{"x":{}}}`), and the SDK's `SecurityRequirement` reader rejects that wrapped form without `list` (`a2a-lf/src/agent_card.rs`, `parse_security_requirement_map`), so the official `a2acli` refused the account-linked card served here. This service names its scopes (`calendar:availability`, `calendar:booking`) so no SDK meets an empty list; verified with `a2acli card` and `send` against the served card. Worth an upstream fix (default the missing `list` to empty).
